# 구현 전 테스트 시나리오 검토

사용자가 요청한 기능/변경의 요구사항·완료 기준을 근거로 예상 동작을 정한다. 구현이 현재 그렇게 동작한다는 이유만으로 기대 결과를 정의하지 않는다.

- packet에 승인된 요구사항, 관련 현재 코드/인터페이스/계약, 기존 테스트 원문 중 관련 부분, 실행 환경·모의 가능 범위를 담는다. 현재 코드·테스트 원문은 `--include <경로>:<a>-<b>`로 붙인다. 구현 전이면 아직 존재하지 않는 코드와 현행 제약을 구분한다.
- 정상·실패·경계·호환성 중 실제 변경과 관련된 사례를 선택한다. 메시지·API 계약 변경은 필요에 따라 식별자 매핑·필드 누락·중복/순서·구버전 수신부를 검토한다. 일반 체크리스트를 기계적으로 전부 추가하지 않는다.
- assessment에 `요구사항 → 사전 조건/입력 → 기대 결과/판정 기준 → 검증 계층·모의 범위`를 제안한다. 핵심 필수 사례와 선택적 사례를 구분하고 기존 테스트가 이미 보장하는 부분은 재사용한다.
- 판단할 수 없는 요구는 질문/미확인으로 남긴다. 핵심 근거가 빠지면 INCOMPLETE다. 테스트 문구를 통과시키기 위한 약한 assertion, 구현을 복제한 기대값, 불가능한 상황을 위한 과도한 테스트를 피한다.
- Codex 호출은 `--mode test-plan` 한 번. 결과는 시나리오 검토이며 실행 증거가 아니다. 메인이 채택한 사례를 기존 구현 담당에게 전달한다. 실환경 검증은 사용자 실행 대상으로 남긴다.
