# 공동 설계 토론 (debate)

Claude와 Codex가 같은 중립 입력으로 **각자 조사·설계한 뒤** 동결·공개·토론·통합한다. 옵션 없음은 A안, `--frozen-critique`는 B안(서로의 비평도 동결 후 공개, 큰 아키텍처 결정용)이다. 결과는 설계 제안일 뿐 구현 승인이 아니다. 사용자가 결정한 뒤 기존 흐름(architect → 승인 → 구현 → 리뷰)으로 넘어간다.

실행기: `S={{SKILL_DIR}}/scripts/co_design.py`. 모든 명령은 JSON 한 줄을 출력하고, 거부·미완료는 종료 코드 2다. 상태는 `python3 $S status --session <sid>`로 본다. 작업 루트(PROJECT)는 **실행 cwd**다(프로젝트 루트에서 실행한다). cwd를 확정할 수 없을 때만 설치 설정의 `project_root`(`{{PROJECT_ROOT}}`)를 쓰고, 환경변수 등으로 바꿀 수 없다. cwd가 `/`·홈·그 상위·임시 영역의 루트처럼 너무 넓거나 홈 아래 숨김 디렉터리(`~/.claude`·`~/.codex` 등) 안이면 모든 명령이 REFUSED다.

- 초안(L1): 메인이 현재 PROJECT의 `.local/cross-check-drafts/<unique>/` 같은 새 일반 초안 디렉터리를 준비하고 `python3 $S ledger scaffold --session <sid> --stage pre-debate|final --out <초안 절대경로>`, `python3 $S synthesis scaffold --session <sid> --out <초안 절대경로>`를 실행한다. 반환 `draft` 경로의 내용을 채워 `validate --file`로 제출하며 최종 저장 경로를 재구성하거나 직접 Write/copy하지 않는다. final 초안은 Codex의 비평·응답·stance를 원문 그대로 넣는다(새 Codex 비평은 `title`=claim, Codex `position`=alternative, codex turn `text`=claim, 응답은 Codex `position`·turn `text`=argument). Claude stance는 `pending`, Claude answer·critique `text`는 빈칸, synthesis 초안은 `adopted_from`·`decision`·`reason` 빈칸과 metrics `-1`이므로 **채우기 전에는 validate가 거부한다**. 기존 파일·보호 경로·심볼릭 링크 경로에는 scaffold가 쓰지 않는다. `--out` 없는 기본 출력(`artifacts/ledger.<stage>.draft.json`·`artifacts/synthesis.draft.json`)과 `--file` 없는 기존 validate는 호환 유지하지만, 기본 초안은 ARTIFACT_ROOT 안이므로 `--file` 입력으로 사용할 수 없다. 새 권장 흐름은 처음부터 별도 일반 초안에 `scaffold --out`을 쓰는 것이다.
- scaffold 응답의 `hints`는 알려진 E/X·쟁점 ID, 입력별 줄 수·정규 인용 예시, 스키마 enum 선택지, 빈 배열로 둔 객체 배열의 요소 형식(`item_shapes`, 예: `user_decisions[]`·`unresolved[]`의 필수 키·타입)만 제공한다. 그런 배열은 `item_shapes`대로 객체를 넣고 문자열로 채우지 않는다. stance·importance·agreement·verification·metrics·adoption은 근거를 보고 직접 결정한다. `freeze --normalize-refs`와 `ledger validate --normalize-refs`는 지정 인용 필드 전체가 `brief.md:2`·`brief:2`처럼 일대일 해석 가능한 경우에만 `brief:L2`로 고치고 입력 범위를 검사한다(scope/index도 지원). 자유 문장·알 수 없는 E/X ID는 바꾸지 않는다. freeze는 기존 원본 경로·생성 시각·상태 검사를 먼저 적용하고 원본 파일을 고치지 않는다. 엄격 검증이 모두 통과할 때만 저장하며 `artifacts/format-revisions/`에 원본 UTF-8·해시·필드별 변경을 남긴다. 옵션 없는 검증·freeze는 기존 동작이다.
- `synthesis validate --derive-checked`는 누락/임의 `codex_checked`를 실제 fidelity의 faithful 판정·요청 coverage·현재 **전체** ledger/synthesis 내용 해시로만 산출한다. 나머지 구조·의미 검증이 모두 통과한 뒤 원자 저장하고 같은 원본/변경 기록을 남긴다. 검증 실패 시 원본은 그대로다. round2·distorted·비요청 쟁점·판정 뒤 내용 변경은 true로 승격하지 않는다. 옵션 없는 validate의 허위 true 거부는 유지한다.
- 요청 형식(새 세션 `lossless-v1`·fidelity 직렬화)은 러너가 자동 적용하며 메인 조작은 없다. `init --compact`·`measure-request`는 사용자가 요청할 때만 쓰고 [러너 상세](debate-runner.md)를 읽는다.
- `reveal`의 `reusable_evidence`(Codex 관측 원문 재사용)는 볼 수 있지만, 사용 직전 현재 파일 해시를 대조하고 변경·누락·충돌·문맥 부족이면 해당 원문을 다시 조사한다. 원자적 스냅샷으로 해석하지 않는다. 최초 독립 조사량·근거 확인·검증·안전 규칙은 재사용 때문에 줄이지 않는다.
- fidelity는 전달된 입장·조건·근거·잔여 위험의 **대표성 확인**만 한다. 기술적 정확성 검증을 완료했다고 보고하지 않는다.

## 절차

**P1-b 메인의 원문 저장:** Agent 결과의 실제 응답 본문 text block을 그대로 복사하고 별도 `agentId`·`usage` metadata는 포함하지 않는다. 끝 개행·닫는 코드펜스·괄호 등 **문자 추가도 금지**한다. 설명·열린 펜스·JSON으로 끝난 응답도 닫는 펜스를 덧붙이지 않고 저장한 뒤 strict 검증 오류를 보고한다. 일반 Markdown 문서처럼 보완하거나 줄바꿈을 정규화하지 않는다. 본문 구분·오류 처리·전송 직전 점검은 [상세 계약과 순수 JSON 예제](architect-handoff.md)를 따른다.

진행은 runner `status`와 짧은 보고로 확인하며 내부 P0~P5를 별도 Task 목록에 중복 등록·갱신하지 않는다. 명시 요청·기존 상위 개발 작업 연결에 필요한 Task는 유지한다.

`init` 응답의 `project_root`를 절대경로 기준 `WS`로 사용한다. 메인의 인계 원본·prepare 출력·부분 초안 `--out`/`--partial-file`은 `$WS/.local/cross-check-drafts/<unique>/...json` 형태의 실제 절대경로로 지정한다. 고유 디렉터리는 먼저 준비하고 `<unique>`는 실제 값으로 바꾼다. 이 안내는 기존 PROJECT·보호 경로·새 파일 검사를 완화하지 않는다.

원장·통합안은 scaffold를 먼저 만들고 **반환 `draft`를 Read한 뒤** `hints`와 `full_base`/Claude slot을 확인해 편집한다. scaffold가 이미 만든 파일을 읽기 전에 새 파일처럼 Write하지 않는다. `hints`·`full_base`·`claude_turn_slots`는 응답 메타데이터이며 draft 안에 복사하지 않는다. 부분 제출은 반환된 envelope를 유지하고 `hints.partial`의 허용 필드만 채운 뒤 반환 `next` 명령으로 제출한다. 기존 placeholder 쟁점은 `issues`로 수정하고 `add_issues`는 새 ID에만 사용한다. 아래 권장 명령은 인용 정규화·checked 산출 옵션을 명시하며, 옵션 없는 기존 CLI의 엄격 거부 동작은 유지한다.

**P0의 준비와 조사를 구분한다.** 메인은 P0~P1-b에서 본문 조사를 하지 않고, 최초 조사는 `architect-prompt` 위임문을 받아 Codex 제안과 동시에 시작한 새 architect만 맡는다. 메인의 코드·원문 대조는 P2 공개 뒤에 수행한다. 이번 실행 중 선행 코드 읽기를 발견하면 중단·보고하며 새 자식으로 위반을 덮지 않는다. 기존 컨텍스트에 있던 이력의 공개·격리와 이번 실행의 새 조사를 혼동하지 않는다. 사용자 제공 사실·요구사항·규칙과 이미 알려진 경로/메타데이터로만 입력을 작성한다. 필수 AGENTS·스킬·스키마 및 경로 존재·브랜치/커밋·변경 파일명/상태 확인은 허용한다. 메인은 대상 코드·테스트·관련 diff/로그·구현 문서 본문 읽기/검색, 외부 조사, 메인이 직접 쓰는 Claude 설계 초안을 P2 공개 전에는 하지 않고(architect 응답의 capture→prepare→freeze는 P1-b 절차다), 조사 에이전트는 위 architect 1개만 시작한다. 입력을 채우기 위해 그 조사가 필요하면 범위·가정을 사용자에게 먼저 질문한다. 기존 컨텍스트에 관련 조사나 결론이 있으면 이를 알리고 P1-b의 새 architect 입력에서 격리한다. 이미 읽었다는 이력을 지우거나 역사적 무오염을 주장하지 않는다.

B안의 Claude 비평을 동결할 때도 별도 일반 초안을 쓰는 동일 경로 규칙을 적용한다.

**원장·통합안 저장:** `ledger validate --file`·`synthesis validate --file`의 초안은 현재 runner의 PROJECT 안에 있는 절대경로의 일반 파일이어야 한다. 다른 PROJECT·다른 세션의 산출물·보호 경로·심볼릭 링크와 ARTIFACT_ROOT 전체·USER_TMP의 `co-design-*` 입력은 거부한다. runner는 구조·의미·참조·명시한 정규화/checked 검증·조건부 계산을 마친 뒤 명시한 `--session`의 `artifacts/ledger.json`·`artifacts/synthesis.json`만 원자 저장하고 실제 `path`·`sha256`을 반환한다. 메인은 그 반환값을 사용하며 최종 출력 디렉터리를 계산·직접 Write/copy하지 않는다. 원본 초안은 바꾸지 않고 의미 있는 내용·문자열·대안·조건·근거·위험은 보존하며, 명시적 인용 정규화와 derived checked 필드만 기계 변경한다. 실패하면 canonical·동결본·audit·세션을 저장하지 않는다. pre-debate 동결본은 덮어쓰지 않으며 허용 상태의 final 원장·통합안은 다시 검증해 갱신할 수 있다. `--session`은 명시 대상일 뿐 같은 스키마 내용의 원래 의도까지 증명하지 않고, 다중 파일 crash transaction이나 outer Claude의 Write 경로 강제 차단도 보장하지 않는다. 잘못된 위치의 쓰기를 발견하면 삭제·이동·덮어쓰기나 새 세션으로 조용히 복구하지 말고 위치·상태를 보고한 뒤 추가 지시를 기다린다. 첫 보호 거부 때에는 아래 중단 규칙이 그대로 우선한다.

**선택적 부분 제출:** `ledger scaffold --partial --stage pre-debate|final --session <sid> --out <새 별도 JSON 절대경로>` 또는 `synthesis scaffold --partial --session <sid> --out <새 별도 JSON 절대경로>`로 시작한다. 새 partial 모드는 현재 PROJECT 안·세션 저장소 밖의 새 `--out`을 필수로 요구한다. runner는 전체 base를 세션의 고정 private `work/partial-bases/`에 배타 저장하고 그 hash를 세션에 기록하며, 반환 `full_base`·`claude_turn_slots`를 보고 별도 draft의 변경 필드만 채운다. `session, kind, stage, base_id, base_sha256`은 바꾸지 않고 `ledger validate --stage <stage> --session <sid> --partial-file <draft>` 또는 `synthesis validate --session <sid> --partial-file <draft>`로 제출한다(`--file`과 배타). 생략한 필드는 base 그대로 보존한다. base 파일 경로·JSONPointer·배열 index·출력 경로를 제출로 지정할 수 없다.

- ledger의 `issues`는 `{issue_id, set?, turns?, add_turns?}` 배열이다. `set`은 `type, importance, title, requirement_ref, claude, decision_method, verification, status`만 받으며 `claude`·`verification`도 필요한 하위 필드만 지정할 수 있다. `turns`는 반환된 Claude `slot`과 `set`(`text, evidence_ids, would_change_if`)만 받는다. 새 Claude turn은 `add_turns`에 기존 전체 turn 형식으로, 새 Claude 쟁점은 `add_issues`에 `issue_id`와 같은 허용 필드 및 `turns`로 명시한다. 새 쟁점의 origin과 빈 Codex 입장은 runner가 만들며 메인이 Codex 입장·stance·turn 원문·근거·would_change_if를 만들거나 수정/삭제하는 경로는 없다. 선택 `states`는 명시한 하위 필드만 갱신한다. final base는 현재 Claude 답변·판정·내용을 유지하고 Codex 결과의 비평/응답 원문을 보강한다. 새로 반영한 각 비평 occurrence에는 별도 빈 Claude 답변 slot이 생기며 채우기 전에는 전체 검증이 거부한다.
- synthesis의 `decisions`는 `{issue_id, set}` 배열이며 기존 decision 필드 중 `issue_id, codex_checked`를 제외한 것만 지정한다. 새 decision도 같은 형식으로 명시하고, `remove_decisions`에 기존 ID를 명시해 미해결로 전환할 수 있다. root `set`은 `required, optional, user_decisions, unresolved, useful_from_codex, useful_none_reason, metrics`를 기존 스키마 형식으로 받는다. 명시 `conditions` 교체·철회 등 판단 변경은 허용하며 합쳐진 전체 내용으로 기존 검증·조건부 판정·fidelity를 거친다. `codex_checked`는 제출할 수 없고 runner가 실제 fidelity coverage와 전체 내용 hash로 항상 derive한다. 내용이 바뀌면 이전 checked가 승계되지 않는다. 초기 빈 decision·metrics sentinel도 이 필드들로 채운다.

부분 제출도 합친 전체 후보에 기존 schema·의미·근거·조건부·checked/finalize 검증을 적용한 뒤 같은 canonical 저장/preflight를 사용한다. legacy 원장에 Codex 비평/응답 원문 turn이 없으면 그 원문을 보강하고 비평별 빈 답변 slot을 추가한다. 기존 답변은 보존하되 그것이 누락 원문의 비평까지 답했다고 추정하지 않으며 새 slot을 채워야 한다. 같은 원문 occurrence가 이미 canonical에 있으면 새 scaffold가 답변을 초기화하거나 빈 slot을 반복 추가하지 않는다. 알 수 없는 필드/ID·중복 issue/decision operation·잘못된 slot·Codex 수정은 저장 전에 거부한다. canonical·동결/근거·관련 Codex 결과·단계가 base 생성 후 바뀌면 `INVALID: stale partial base`인 일반 optimistic conflict로 반환한다. 자동 rebase나 옛 patch의 무조건 재적용은 하지 말고, 반환 next대로 새 base를 받아 변경 근거를 확인한 뒤 다시 제출한다. 성공 후 추가 변경이나 fidelity 뒤 재derive도 새 base에서 시작한다. 같은 trusted base의 내용은 canonical/의존성이 그대로일 때만 다시 사용할 수 있다. base 변조·훅/permission/보호정책 거부는 일반 stale 충돌과 다르며 아래 첫 거부 중단 규칙을 따른다. B안 독립 Claude 비평의 pre-freeze는 기존 full `freeze --side claude-critique`로 유지하고, B안 final 원장·synthesis는 부분 제출을 지원한다.

**구조화 architect 인계:** P1-b 위임에 [출력 계약·전체 예제·원본 보존/오류 처리](architect-handoff.md)와 `scripts/debate/schemas/proposal.schema.json` 경로를 포함한다. file 근거의 범위·ref·hash는 고정 위임문이 안내하는 읽기 전용 `evidence inspect`의 반환값을 그대로 쓰며 범위를 추측·자동 보정하지 않는다. 일반 architect Markdown 형식 대신 JSON 하나로 반환하며 `design.components/flows/contracts`는 `string[]`, 비파일 근거는 `E<n>`이다. 메인은 최종 응답 텍스트 전체를 그대로 저장하고 JSON 추출·앞뒤 설명/펜스 제거·재직렬화를 하지 않는다. 설명이 섞이면 strict JSON 거부 후 원문 보존·중단·보고한다. 새 메시지는 정확히 `{handoff_version: 2, proposal: <기존 proposal.schema.json의 전체 object>, evidence_manifest: [...]}`다. 관찰문은 proposal의 evidence에만 한 번 작성하고 manifest에는 넣지 않는다. proposal의 side는 `claude`이며 요구사항·설계·대안·조건·위험·검증·미확인·부가 설명을 모두 기존 필드에 담는다. file 근거의 `id`는 `local:source_a` 같은 로컬 키, `ref`는 실제 `relative/path:L1-L2` 또는 절대경로의 같은 범위이고, manifest 각 항목은 정확히 다음 필드를 갖는다.

```json
{"key":"local:source_a","path":"/absolute/current/project/src/file.py","lines":[1,2],"file_sha256":"현재 전체 파일 sha256","source_state":{"worktree":"/absolute/current/project","checked_at":"2026-11-17","status":"Git 여부·branch/commit·관련 로컬 변경 또는 Git 미사용"}}
```

모든 file 근거는 유일한 manifest와 일치해야 한다. v2의 관찰문은 proposal.evidence[].observation 원문 하나를 local key로 연결해 등록 entry에 그대로 복사한다. 문장 생성·요약·비교 판단은 하지 않는다. 무태그 legacy 형식은 기존처럼 양쪽 observation을 요구하고 정확히 일치해야 하며, 불일치한 옛 메시지를 자동 변환하지 않는다. runner는 현재 PROJECT의 파일·범위·현재 hash·관찰 매핑을 검사한다. `source_state.worktree`는 PROJECT 자체 또는 해당 파일을 포함하는 PROJECT 안의 실제 하위 작업트리(app/edge 등)이며 보호 경로·외부·심볼릭 링크는 허용하지 않는다. `source_state.status`는 architect가 보고한 저장소별 상태이며 git 내용까지 자동 인증하는 값이 아니다. 기존 등록 command/mcp/web의 kind·ref와 비등록 brief/inference·선택 data 원자료 참조는 기존 의미 그대로 유지하고 file로 승격하지 않는다. 기존 semantics가 요구하는 등록이 없는 command/mcp는 계속 거부한다. web은 ref가 http(s) URL 하나일 때만 등록 없이 허용한다(비등록 E ID라 원장 근거로는 인용 불가). 로컬 키는 선언된 evidence `id`에서만 정확히 변환하고 자유 문장/ref에 로컬 키가 남으면 추측 치환 없이 등록 전에 거부한다. 기존 등록 ID와 비등록 proposal ID를 함께 예약해 새 ID가 충돌하지 않으며 이후 `evidence add`도 같은 예약을 따른다. 메시지/전체 schema·생성 시각·전건 capture·별도 새 출력 경로 검사를 끝내기 전에는 근거·초안·세션을 저장하지 않는다. prepare 뒤 기존 freeze는 메인만 실행한다. Agent 결과의 `output_file`은 그 architect의 transcript(`subagents/agent-<id>.jsonl`로의 심볼릭 링크)이며, 메인은 `proposal capture`로 그 파일 하나에서만 최종 메시지를 원문 그대로 한 번 저장한다. transcript 전역 검색·새 Claude subprocess·architect 파일 쓰기·별도 raw notes 보관으로 우회하지 않는다. 재작성·ID 오류·Codex 원문 전사를 줄이려는 기능이며 실제 절감이나 조사/추론 품질 동등성을 측정한 것은 아니다.

**거부 처리:** 첫 훅·permission·보호정책 거부부터 현재 workflow를 중단하고 사용자에게 보고한다. 자식은 즉시 메인에 알리고, 메인도 추가 호출·동결·정리를 실행하지 않는다. `rm`→`rm -f` 같은 flag 변경, 다른 명령/도구/경로/프로필 사용, 설정 변경, 기존 요청을 삭제 승인으로 해석, 자식이 거부당한 동작을 메인이 대신 실행, 다른 새 세션을 통한 우회도 하지 않는다. 훅·permission·보호정책 거부에는 이 중단 규칙이 P5와 stale 회수 뒤의 `finalize` 안내보다 우선한다. 이 경우 `finalize`·새 보고서 파일 생성도 중단하고 허용된 기존 기록·`status` 조회와 채팅 보고만 한다. 보호 거부가 아닌 다른 STOPPED의 기존 보고 절차와 runner의 `finalize` 기능은 유지한다. architect 인계 오류는 [원본 보존 규칙](architect-handoff.md)에 따라 수정하지 않고 중단·보고한다. 그 밖의 보호 거부가 아닌 로컬 초안 schema·줄 범위 입력 오류(원장·통합안 등)는 원인을 확인한 뒤 수정할 수 있지만, 동일 실패 2회 뒤 새 근거 없이 반복하지 않는 기존 규칙은 유지한다. 거부 분류가 불명확하면 중단·보고한다. 이 지침은 outer Claude의 도구 실행을 강제 차단하거나 실제 준수를 증명하지 않으며 별도 설정/훅을 추가하지 않는다.

## 최종 보고 형식 (A·B안 공통)

- 채팅 최종 보고는 최초 제안 비교표·쟁점별 토론/결론 표·사용자 결정/미해결을 중심으로 짧게 쓰고 상세 `report.md` 경로를 연결한다. 보고서 1~11절을 다시 풀어 쓰지 않되 중요한 조건·위험·미검증·Codex 확인 상태를 생략하지 않는다.
- 쟁점 표 뒤에 **외부 조사 표**를 둔다. `report.md` 11절에서 최신 동향·일반적인 구현·기술·관련 논문을 구분하고, 항목마다 요점(논문은 제목·연도·관련성)·링크·제출 측·링크 확인 결과를 적는다. 최종 결정에 영향을 준 조사 결과는 해당 쟁점 ID를 함께 적는다. 양측 모두 조사하지 않았으면 그 사유를 한 줄로 적는다. 링크 확인이 `mismatch`·`unreachable`·미확인인 항목은 그대로 표시하며 근거로 쓰지 않는다.
- 사용자에게 보고할 때 `report.md` 1절의 **최초 제안 비교표**를 먼저 보여준다. 분량에 맞춰 요약하되 양쪽 핵심 제안·차이·중요 전제와 미확인을 보존한다. 원본은 토론 전 동결한 `artifacts/claude/proposal.json`·`artifacts/codex/proposal.json`이다. 최종 원장 입장을 최초안으로 바꾸어 쓰지 않는다.
- 이어서 기존 원장·통합안으로 아래 **쟁점별 토론·결론 표**를 작성한다. 중요 쟁점마다 한 행을 쓰고 상세 내용은 보고서의 같은 쟁점 ID로 연결한다.

  | 쟁점 ID·내용 | Claude 최초 입장 | Codex 최초 입장 | 상대 지적·응답 요약 | 최종 제안·변경 이유 | 합의·미해결 / Codex 확인 |
  | --- | --- | --- | --- | --- | --- |
  | 원장 ID·쟁점 | 최초안 근거 위치와 요약 | 최초안 근거 위치와 요약 | 누가 무엇을 지적하고 어떻게 답했는지 | 유지·수정·기각·통합 결과와 이유 | 원장 상태와 Codex 확인 여부를 구분 |

- 최초안에 없는 쟁점은 `최초안에 명시 없음(토론 중 추가)`, 한쪽 산출물이 없으면 `미작성/확인 불가`로 쓴다. 제안 항목의 순서나 비슷한 표현만으로 같은 쟁점이라고 짝짓지 않으며, 연결을 확인할 수 없으면 `대응 미확인`으로 남긴다. 합의와 사실 검증·Codex의 통합안 확인은 구분한다.
- 두 표는 기존 산출물로 작성한다. 표를 채우기 위한 추가 모델 호출·토론은 하지 않는다. `--review`·`--test-plan`·`--code-review`에는 독립 최초안 두 개가 없으므로 이 형식을 강제하지 않는다.

## 원장 규칙 (`ledger.schema.json`)

- 근거 연결(`*_links.json`·summary `links`): 파일 인용(`path:Lx-Ly`)은 같은 세션의 **완료된** 셸 도구 기록이 같은 파이프라인 안에서 그 파일의 해당 범위를 읽었고(`sed -n 'a,bp' 파일`, `nl`/`cat 파일 | sed -n 'a,bp'`, `head -n N 파일`, 범위 지정 없는 `cat`/`nl` 전체 읽기, 또는 `rg -n`/`grep -n` 출력에 해당 줄 번호 전부) 출력이 인용 범위 줄 수 이상이면 `excerpt`, 그 밖의 경로 일치는 `mention`이다. 읽은 뒤 후단에 `head`·`tail`·`grep` 등 필터가 있거나, 범위가 다른 파이프라인(`&&`·`;` 뒤)의 것이거나, 출력이 비었으면 `mention`이다. 등록된 Claude 근거(`E<n>`)와 그 범위 안 인용은 `excerpt`, URL·자유 문구는 `mention`. 기존 `linked` 키는 `excerpt + mention`으로 유지한다.

- 쟁점 ID는 `I<n>`(Claude)·`C<n>`(Codex 비평) 등 대문자+숫자이며 Codex 출력의 `issue_id`와 같게 쓴다. 입장은 `pending|proposed|accept|reject|conditional|open`, 판정 방법은 `pending|source-text|reproduction|user-decision|undecidable`이다.
- high·medium 쟁점은 최종 단계에서 양측 stance와 판정 방법이 모두 있어야 한다. `type=fact`는 사용자 결정으로 판정하지 않으며, confirmed/refuted에는 방법과 근거 ID가 필요하다. 근거 ID는 등록된 `E<n>`, Codex 제안의 `X<n>`, `brief:Ln`·`scope:Ln`·`index:Ln`만 쓴다.
- Claude가 실행한 결과는 관찰 출처의 하나일 뿐이다. 두 AI의 합의는 증거가 아니며 합의율·채택률을 품질 지표로 쓰지 않는다.
- 상태는 실행(`states.execution`)·근거 충분성·합의를 분리해 기록한다.

## 조건부 호출 판정

1. `round2`: 토론 후 등록한 새 근거로 high 쟁점의 verification·status가 바뀌었거나 사용자가 요청(`--user-requested`).
2. `fidelity`: 1이 아니면서 high 쟁점이 통합안에서 빠짐, Codex 최종 stance가 accept가 아닌데 Codex 안 이외(`claude`·`both`·`neither`·`evidence`)를 채택, ledger의 Codex stance가 Codex 출력과 다름, Codex의 조건부 입장이 결정 조건에 없음. 계획의 "토론 후 Codex 입장의 잔여 위험 변경" 비교는 구현하지 않았다(잔여 위험은 자유 서술이라 기계 비교 불가). 해당하면 사용자 요청(`--user-requested`)으로 round2를 쓰거나 미확인으로 보고한다.
3. 둘 다면 round2 먼저. 예산(호출 상한·Codex 누적 예산 잔여 60초 미만·이미 사용)이 없으면 `next=none`, `blocked`에 이유가 남는다. 계산된 이유가 없거나 통합안·ledger가 계산 뒤 바뀌었으면 호출이 거부된다.

## 실행 한도·정지·버전 게이트 (요약)

상세(요청·결과 크기 한도, 실시간 감시 항목, E2E 실측, 버전 자동 점검 조건, 산출물 보존 경로)는 [러너 상세](debate-runner.md)에 있다. `init`이 버전 게이트·자동 점검으로 거부하거나 점검 경고를 냈을 때, `call`이 STOPPED·INCOMPLETE·BUDGET로 끝났거나 감시 정지 사유를 해석할 때, 보존·정리(`prune`)를 다룰 때 해당 절을 읽는다.

- 호출 상한 A안 3회·B안 4회(실패 포함, 자동 재시도 없음). 시간 제한은 Codex 쪽에만 둔다: 단계 상한 proposal 900초·그 밖 600초, Codex 누적 예산 A안 1800초·B안 2400초. Claude 시간은 세지 않는다.
- scope의 `allowed_tools`에 `web`이 있을 때만 Codex web_search를 켠다(debate 기본값은 켬, `--no-web`이면 끔).
- proposal 단계 정지 시 남는 `partial_messages.md`는 공개 전 Codex 소견이므로 사용자에게만 보고하고, 같은 질문을 다시 돌리기 전 Claude는 읽지 않는다.
- 모델이 스스로 낸 INCOMPLETE(근거 부족, 응답 누락)는 조건부로 진행한다. 정지 후에는 `finalize`로 보고만 하고 재시도·우회하지 않는다.
- 버전이 바뀌면 `init`이 자동 점검한다. 재시도로 통과했다는 경고가 나오면 사용자에게 알린다. FAIL이면 거부 사유·로그 경로를 보고하고 멈춘다. `verify-codex` 단독 점검은 task-metrics 기록 대상이 아니다.
- 산출물 `.local/co-design/<sid>/artifacts/`·`work/`는 자동 삭제하지 않는다(사용자가 결정하면 `docs/`로 옮긴다). `python3 $S prune --apply`는 사용자가 승인한 경우에만 실행한다.
- task-metrics: `finalize`·`reveal` 출력의 `call_summaries`(실재하는 호출별 summary 경로)를 호출마다 `--workflow debate --cross-check-summary <summary.json>`으로 한 번씩 기록한다.
