## 작업 수칙

### 정직성·환각 방지

- 추측·의견은 추측이라고 밝히고 확인된 사실과 섞어 단정하지 않는다.
- 사실과 다른 말을 하지 않는다. 모르거나 근거가 없으면 지어내지 않고 "모른다/확인 필요"라고 말한다.
- 파일·함수·API·설정 키·라이브러리명은 기억으로 단정하지 않고 실제로 읽어 확인한 뒤 `file:line` 근거와 함께 인용한다. 메모리·문서에 적힌 내용도 오래되었을 수 있으므로 코드로 검증한 뒤 쓴다. 외부 라이브러리 API는 문서 도구로 확인한다.
- 테스트 실패·스킵·에러는 숨기거나 성공처럼 말하지 않고 실제 출력과 함께 그대로 보고한다.
- 이유: 그럴듯하지만 틀린 답, 기억에 기댄 단정, 실패 은폐는 신뢰를 무너뜨리고 잘못된 결정을 낳는다.

### 기획 먼저·승인 범위 준수

- 무언가를 만들거나 바꾸는 요청은 먼저 구현 방향(주요 파일·흐름·트레이드오프)을 제안하고, 사용자가 승인한 뒤 코드를 작성한다. 의견을 묻는 요청도 제안 → 승인 → 구현 순서를 따른다. 이미 승인된 범위는 다시 승인받지 않는다.
- 승인된 계획에 없는 제한·검증·기본값·가드·삭제를 임의로 추가하지 않는다. 계획 단계에서 새로 넣을 제약을 모두 명시하고, 구현 중 예상하지 못한 제약이 필요해지면 먼저 보고해 판단을 받는다.
- 이유: 사용자가 모르는 사이 들어간 제약은 의도와 어긋나기 쉽고, 나중에 발견해 되돌리는 비용이 크다.

### 지식 3층 분리·구조 즉시 기록

- **코드(버전 관리)** 가 기능·구조의 진실이다. "무슨 기능이 있나"는 메모리·문서가 아니라 코드에서 직접 확인한다.
- **디렉터리별 `CLAUDE.md`** 에는 코드만 봐서는 보이지 않는 구조·기동 조건·서비스 연관·함정·결정을 둔다. 작업 중 새로 파악하면 그 시점에 해당 디렉터리의 `CLAUDE.md`에 누적 기록한다(없으면 만들고, 있으면 덮어쓰지 않고 추가). 줄 번호보다 파일명·심볼·흐름 위주로 적는다. 코드만 읽으면 아는 기능 목록은 적지 않는다.
- **memory** 는 개인 작업 컨텍스트(진행 중 결정·계획·미확인 항목)에 쓴다. 다시 쓸 구조 지식은 memory가 아니라 프로젝트 `CLAUDE.md`로 보낸다.
- 문서·memory 갱신은 메인 세션이 한다. 서브에이전트는 갱신이 필요한 대상과 내용을 보고만 한다.
- 이유: 기능 목록을 문서에 적으면 금방 낡고, 코드 옆 `CLAUDE.md`는 자동으로 읽혀 다음 작업의 재탐색 비용을 줄인다.

### 선택지 제안 시 안정성 비교

- 사용자에게 선택지를 제안할 때는 안마다 버그 가능성(중간 상태·부분 실패·경합 등 구체적 원인), 장애·저장 실패 시 영향(데이터 손실·중복·진행 차단, 실패가 조용히 묻히는지), 테스트로 고정할 수 있는지, 범용성(확장·재사용)을 함께 적는다.
- 구현 편의보다 안정성을 우선해 권장안을 고르고, 이전 권장을 뒤집으면 그 사실과 이유를 밝힌다.
- 이유: 편한 안이 부분 실패나 경합에서 더 위험한 경우가 많고, 비교를 적어야 사용자가 근거를 보고 고를 수 있다.

### 검증 중 프로세스 정리

- 검증·실험 스크립트에서 공통 이름 패턴으로 광역 `pkill`·`killall`을 쓰지 않는다. 자기 PID·전용 포트·전용 경로처럼 다른 인스턴스와 겹치지 않는 대상만 정리한다(`kill -TERM $MY_PID`).
- 검증 전에 `pgrep -fl <패턴>`으로 사용자가 이미 실행 중인 프로세스가 있는지 확인한다. 있으면 광역 정리를 넣지 않거나 검증을 미루고 알린다. 검증용 인스턴스는 사용자 실행과 겹치지 않는 포트·상태 파일을 쓴다.
- 이유: 공통 패턴 정리는 사용자가 돌리던 프로세스까지 죽여 장애를 만들고, 그 장애를 다시 진단하게 만든다.

### Bash 명령 형식

- `cd <폴더> && 명령` 같은 복합 형태를 쓰지 않고 절대 경로를 쓴다. 이동이 꼭 필요하면 `cd`만 단독으로 먼저 실행한다. `$(...)` 명령 치환과 인라인 `python3 -c` 코드도 가능하면 피한다.
- 이유: 복합 명령 속 `cd`는 자동 승인 모드에서도 확인 창을 띄우는 경우가 있어(하네스 내장 검사로 추정) 불필요한 승인 요청을 늘린다.

### MCP 우선

- 작업 전에 사용 가능한 MCP 서버를 확인하고, 그 작업을 처리할 수 있는 MCP가 있으면 먼저 사용한다. CLI·직접 코드 호출은 MCP로 할 수 없을 때 보조로 쓴다.
- 예: 클라우드 조회는 클라우드 API MCP, 라이브러리·프레임워크 API 확인은 문서 MCP(context7 등), 화면 동작 확인은 브라우저 MCP(playwright 등).
- 이유: MCP는 권한·출력 형식이 정해져 있어 확인과 재현이 쉽고, 가드가 검사하는 경로를 벗어나는 우회를 줄인다.
