## 작업 대상과 역할

- `<하위 경로 1>/`: <구성·언어·역할>. `<하위 경로 2>/`: <구성·언어·역할>.
- 작업할 하위 경로의 `CLAUDE.md`가 있으면 따른다. 구성·개발/빌드 명령이 필요할 때만 <프로젝트 참조 문서 경로>를 읽는다.
- **<계약 경계 이름>:** <예: API·메시지 토픽·페이로드·식별자·파일 포맷>은 송신/수신 양쪽을 확인한다.
- 에이전트 정의: `.claude/agents/`(프로젝트) 또는 `~/.claude/agents/`(공용). `architect`는 전체 설계, `troubleshooter`는 진단, `code-reviewer`는 정적 리뷰(세 역할은 읽기 전용). 구현은 <영역>=`<영역>-feature`(`feature-template.md`에서 생성), 그 밖의 지정된 공용·독립 스크립트=`script-feature`가 맡는다.
- 담당은 언어가 아니라 경로·역할로 정한다. 메인이 수정 파일·완료 기준을 지정하고 다른 작업의 변경을 보존한다. 보호 설정·훅·하네스 원본은 독립 스크립트 일반 권한에 포함하지 않는다. 사소한 변경은 메인이 처리할 수 있다.

## 설계·구현·검증

- 주요 변경: `architect` 계획 → 사용자 승인 → 담당 구현 → `code-reviewer` → 검증·보고. 이미 승인된 범위를 중복 승인받지 않는다. 문제 진단은 `troubleshooter`가 맡는다. 위임은 메인만 수행하고 서브에이전트끼리 호출하지 않는다.
- 사용자는 원하는 동작을 설명하면 된다. 메인/architect가 현행 코드·계약을 조사해 **원하는 동작·변경 범위·호환성·필수 검증·완료 판정**을 구체화한다. 기존 계획에 필요한 만큼만 기록하고 구현·리뷰에 전달한다. 기술적으로 확인 가능한 사항은 해결하고, 미정인 사용자 선호·동작·계약·범위만 질문한다. 필수 구현과 선택적 개선을 구분한다.
- 중요한 예외가 나오면 계획·완료 기준을 갱신한다. 사용자 동작·계약·범위가 달라지면 확인하고, 완료 시 기준별 결과와 미해결 사항을 보고한다.
- 위임에는 요청·배경·경로·결정·완료 기준·검증 방법을 자기완결적으로 전달한다. 새 채팅 인계나 복잡한 위임에만 `handoff` 스킬을 사용하고 짧은 위임은 메시지로 끝낸다.
- 리뷰 입력은 요구사항/계획/완료 기준, 저장소·작업트리·비교 기준, 변경 파일/내용/의도, 계약 경계다. **각 하위 저장소의 Git 여부를 확인**하고 staged/unstaged·관련 새 파일을 포함한다. Git 미사용 경로는 변경 목록·기준본으로 검토한다. 중요 변경은 리뷰하고 동작·권한·계약에 영향 없는 사소한 편집은 생략한다. Blocker는 구현 담당이 수정하며 리뷰어는 코드 수정·테스트를 실행하지 않는다.
- 설계에서 수정 중 관련 테스트와 완료 시 필수 통합·회귀 검사를 정한다. 계약 경계 변경은 양쪽 스키마와 연동을 검증한다. **프로젝트별 필수 테스트·커버리지 기준은 유지**한다(<예: `npm run test`, coverage branch 85%>). 영향 범위가 불명확하면 검증을 넓힌다.
- 재사용할 탐색 근거는 기존 계획/메모에 파일·근거 위치, 호출 흐름·계약, 결정·미확인 사항만 남긴다. 검증은 명령·cwd/대상·결과·코드/입력/환경 조건을 기록한다. 변경·모순·새 결함에 영향을 받는 부분만 다시 읽고 검사하며, 필요한 원문을 요약 누락 때문에 생략하지 않는다.

## 문서와 코드 상태

- 코드 사실을 담은 설계·구조 설명·메모·memory·인계에는 저장소/작업트리 경로, 확인 날짜, 브랜치·커밋, 추적/미추적 로컬 변경, 근거 파일·위치를 기록한다. 여러 저장소는 각각, detached HEAD·Git 미사용·미확인은 그대로 표시한다. 일반 작업 규칙에는 불필요하다.
- Git 저장소는 <Git 저장소 목록>뿐이다(<확인 날짜> 확인). <Git 미사용 폴더 목록>은 Git 미사용이다. 새 저장소가 생기거나 바뀌면 이 줄을 갱신한다.
- 재사용 시 현재 상태와 대조한다. 기준 누락·브랜치/커밋/관련 로컬 변경 차이가 있으면 필요한 diff/원문만 확인한다. 커밋이나 동일한 dirty 표시만으로 로컬 내용까지 같다고 판단하지 않는다. 필요하면 관련 파일 해시를 사용한다. 과거 사실은 적용 상태를 구분해 보존하고, 브랜치명만 바꿔 최신 근거로 만들거나 문서 전체를 일괄 갱신하지 않는다.
- 필요할 때만 `python3 <HARNESS_HOME>/tools/repo_context.py --repo <작업트리>`로 기준을 수집한다(`--repo` 반복 가능, 관련 파일은 `--file <경로> --hash`; 상대경로는 실행 cwd 기준). 잘린 목록의 임시 파일·생략 수와 `INCOMPLETE`/오류/미확인 범위를 보존한다. 결과는 원자적 스냅샷이나 코드 검토 증거가 아니며 매 턴 실행하지 않는다.

## 실환경 경계

- **<클라우드·장비 등 실환경> 배포·수정·추가·삭제는 사용자만 실행한다.** 메인/서브에이전트는 로컬 코드·템플릿·사용자 실행 절차만 준비한다. 구현·테스트·검증 요청도 실환경 변경 승인이 아니다.
- 모든 경로(MCP·CLI·SDK·콘솔/브라우저·SSH/SSM·CI/CD)에 적용한다. 데이터 쓰기/업로드/삭제, 메시지 발행·제어 명령, 서비스 시작/중지도 포함하며 test/build/dry-run 이름만으로 안전하다고 판단하지 않는다.
- 조회는 <읽기 전용 프로필·자격> 으로 MCP 우선, 필요하면 CLI를 쓴다. 다른 프로필·자격증명·도구로 거부를 우회하지 않는다. 인증 갱신은 메인이 환경을 확인하고 <갱신 절차>로만 한다. 비밀값은 읽거나 출력하지 않고 조회 가능 여부로 확인한다.
- 로컬/모의 검증을 먼저 완료한다. 실환경 검증은 사용자 실행 명령·대상·영향·확인 방법과 미검증 상태를 보고하며, 사용자 제공 결과와 직접 실행 결과를 구분한다.

## 선택 도구와 작업 기록

- 큰 로그 집계·근거 재확인·독립 로그 배치가 입력/호출을 줄일 때만 `efficient-investigation` 스킬을 사용한다. 짧은 탐색·출력은 기존 도구로 처리한다.
- 사용자가 교차검증을 요청한 경우만 `cross-check` 스킬을 따른다. 옵션 없이는 양측이 각자 조사·제안 후 토론하는 debate(큰 결정은 `--frozen-critique`), 단방향 검토는 `--review`, 테스트 시나리오는 `--test-plan`, 구현 리뷰는 `--code-review`다. 교차리뷰와 기존 리뷰가 겹치면 미확인 부분만 보완하고 필수 검증은 유지한다.
- 기능 구현·버그 수정 등 의미 있는 작업 완료 시 메인이 `task-metrics` 스킬에 따라 기존 검증과 함께 로컬 기록 1건을 남긴다. 짧은 질의/사소한 편집은 생략한다. 이미 기록된 실행은 반복 기록하지 않고 확인된 수치만 사용한다. 미확인은 null로 남기며 측정을 위한 추가 AI 호출·원문 로그 수집은 하지 않는다. 비교 요청 때만 집계한다.
